EPS firmware 3.1: executive summary

v3.1 is the current final firmware. It replaces the network layer of the EPS with one written for the job (v3.0) and brings it in line with the network standards a device on an enterprise network is expected to follow. Where v2.2 needed a power cycle after the network failures we reproduced, v3.1 recovers by itself, and it records what happened when something goes wrong. It has passed every bench test; it has not yet run in the field.

Status 2026-10-11 · Bench: three units on a NETGEAR M4250 (a switch model with field failures), then a real EPS box cabled to a PC · All tests pre-registered, every failure reported

Bottom line

Field problem: EPS units on v2.2 randomly drop off the network (no ping, no web page, no control) until their power is cycled.

What we found: v2.2 has several defects that lead to exactly that state. The clearest one: in DHCP mode, a single DHCP renewal that goes unanswered makes v2.2 restart itself, and if the DHCP server is away at that moment, the unit stays off the network until someone power-cycles it. Others: the network chip losing its settings (v2.2 never notices), and connections that block the control port. For units set to a static address, the field trigger is still open.

v3.1: recovers by itself from every one of these in our tests, typically within seconds, keeps the outputs on while it does, and keeps a log that will tell us what happened if a unit does drop off in the field. On a pre-registered suite of 56 network-standard requirements it passes 46; v2.2 passes 26. We are confident v3.1 is a large step up in network robustness. Whether it ends the field dropouts will be shown by a pilot, not by the bench.

Why v3.1 still fails four standards

  • Network chip limits (2): the W5500 corrupts long ping payloads and can't reassemble fragmented packets. No firmware on this board can change that; v2.2 fails the same two.
  • Small, fixable (3): too many ARP requests to an absent gateway (about 20 a minute); no 400 when the Host header is missing; 400 instead of 414 for an over-long URL. v2.2 fails all three as well.
  • Kept on purpose (3): the web page and control systems switch power with simple GET links; a stalled receiver is dropped after 2 s so it can't hold up power control; while waiting for a DHCP server the unit asks from its fallback address, so it stays reachable.

Is v2.2 as good, since both fail four?

  • No. One failed item fails a whole standard, so the count of failed standards hides the size of the gap: v2.2 fails 25 requirements, v3.1 8.
  • Only v2.2 takes an IP address already in use, asks for DHCP once a second, renews and rebinds incorrectly, drops TCP connections after 18 s, and treats every HTTP method as a GET.
  • The standards suite doesn't test recovery from the field failures, where the gap is largest (table above).

What we can say, and what we can't yet

We can say

  • v3.1 recovers by itself, in seconds, from every v2.2 failure we could provoke on it: DHCP outage, lost chip settings, stuck connections.
  • v3.1 behaves like a standard network device on the points that matter on a shared network: DHCP, address conflicts, unique MAC, no stuck connections. Its remaining standards gaps are listed above.
  • If a v3.1 unit ever drops off, its log will show why: link, chip, DHCP, address conflict or restart.

We can't say yet

  • That v3.1 ends the field dropouts: the trigger for static-mode units is still open.
  • How it handles the rare deaf state after a link negotiation: it hasn't occurred on the new firmware yet (0 in 300).
  • How it behaves with real loads switching, over days, and on other switch brands.
  • Results rest on three boards and three days of testing; the same team wrote the firmware and the tests (mitigated by pre-registered criteria and crossover runs).

Recommended rollout

  1. Hands-on checks on the real box: inputs, factory reset and LED colours by hand; real power cycles with the USB cable unplugged.
  2. Real loads: v3.1 on our showroom unit, loads switched while the log runs. Any chip re-init in the log is a finding.
  3. Pilot: v3.1 with per-unit MACs on units at sites that had dropouts. With no failure in N unit-days, the 95 % upper bound on the failure rate is about 3/N (≈ 300 unit-days to show fewer than one failure per 100 unit-days).
  4. Site settings: static addresses outside DHCP ranges, or DHCP reservations; EPS on an untagged access port in the AV VLAN.
  5. On any dropout, before power-cycling: note the LED colour, check whether the unit's MAC is still in the switch's MAC table, then read NET_LOG after it is back.
  6. Fallback: v2.2 can be re-flashed.
