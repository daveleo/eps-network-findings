EPS network failures: investigation report

Expromo EPS power sequencer (Keyestudio KS0304: ATmega328P + WIZnet W5500), firmware v2.2 vs v3.0, v3.1, v3.2 and v3.3 Bench work 2026-10-08 13:00 – 2026-10-12 morning · Repo daveleo/EPS · Status as of 2026-10-12 · v3.3 is recommended as the official firmware (v3.2 + the gaps a code analysis found; see §5.25–5.26)

1. Summary

Units in the field drop off the network at random: no ping, no web page, no TCP control, until power is cycled. No failed unit has been examined in its failed state. Field units are usually set to a static IP; some AV networks have a DHCP server, sometimes not.

On the bench (two bare KS0304 boards on USB power, and since 2026-10-09 afternoon a real EPS box with its 10 V supply, six SSRs and the 22 µF reset capacitor; NETGEAR M4250 switch, a model with field failures):

  1. The field symptom means the W5500 is not answering at all. The chip answers ping and ARP by itself. v2.2's socket starvation leaves ping working, so it can't be the field failure on its own.
  2. Three mechanisms reproduce the full symptom on v2.2:
    • (a) DHCP mode: a DHCP outage strands the unit until it is power-cycled (measured with the M4250's DHCP server, §5.20). One unanswered renewal makes v2.2 restart itself: the Ethernet library's DHCP loop blocks longer than v2.2's 8 s watchdog. If the server doesn't answer within 60 s of that restart, v2.2 falls back to its static address and never asks again; with the server back it stays unreachable (link up, still transmitting) until restarted. A power cycle brought it back in 13 s. With this server v2.2 also restarted itself every ~4 min while the server was up. v3.0 recovered by itself in every case. Applies only to units in DHCP mode.
    • (b) The W5500 loses its settings (the effect of a supply dip or ESD, reproduced by one register write): v2.2 dead until reset (4/4); v3.0 recovers in 3–6 s (5/5). The real trigger is untested: no real loads switched yet; mains cuts of 0.2–10 s on the real box caused nothing (18/18).
    • (c) The W5500 goes deaf after a fresh link negotiation: link up, transmits, receives nothing, registers correct. On one board (unit 2): 4 in ≥ 536 resets and 1 in 134 switch-port flaps; once it cleared by itself after 97 s. Whether it can last until a power cycle is unknown: earlier tests always reset the unit after 60 s.
  3. Static-mode field failures are not explained yet. IP address conflicts are excluded (field knowledge). Remaining candidates: (b) triggered by load switching, and (c).
  4. v2.2 also has network defects of its own that cause partial failures (two idle connections block the control port while ping works; the web page blocks control for ~0.9 s; the stall watchdog can't see either). Part of this is the Arduino Ethernet library itself, which also writes its retry settings to W5100 register addresses on the W5500 (RTR = 72 ms, RCR = 8 instead of 200 ms × 2; §5.19).
  5. v3.0, a rewrite of the network layer, beats v2.2 on every pre-registered criterion except one lost ping, recovers from (a) and (b), and kept its lease through every DHCP event. v3.1 (v3.0 + network-standards work: DHCP timing and DECLINE, address conflict detection, TCP timers, HTTP methods, syslog) re-ran every non-soak test on its final build on the real box and passed (§5.22). v3.2 (v3.1 + a wider W5500 self-check covering the mode, retry and PHY registers) recovers from all 14 single-register chip faults — including the PHY power-down that reproduces the field symptom, which v2.2 and v3.1 both die on — with no regression (§5.24). v3.3 (v3.2 + the four gaps the code analysis of §5.25 found: the PHY reset bit, a link that stays down, a receiver check that works without a gateway and after a link-up, and a supply monitor) recovers from all 17 single-register faults including a PHY held in reset, on which v3.2 is dead, and passed the full regression overnight (§5.26); it is recommended as the official firmware. None is field-proven, and none has run on a box with real loads.
  6. Corrections made on 2026-10-09 (§5.17–5.19): a USB/DTR reset also resets the W5500 (its link renegotiates), so the deaf start-ups followed a W5500 hardware reset, not a CPU-only restart; the H4c rationale ("v2.2 never resets the PHY") is void; v2.2's own watchdog restarts never produced a deaf state (0 in 19+). Finding #7 (retransmission "3 tries, ~1.4 s") was wrong because of the library defect.
  7. Code analysis (§5.25): v2.2 cannot make a static unit stop answering by its own logic; the field failure needs an outside upset of the W5500, which v2.2 can never leave. The leading trigger hypothesis is a supply sag: the board's brown-out level is 2.7 V (measured on unit 3), below what the CPU (3.78 V at 16 MHz) and the W5500 (2.97 V) need. Untested: it needs USB unplugged.
  8. Standards (§5.23): on a pre-registered suite of 56 requirements from 10 standards, run on the same box, v3.1 passes 46 and v2.2 26. By standard, v3.1 passes 6 (IEEE 802.3, IEEE 802 MAC, ARP, RFC 5227, 802.1D, syslog) and v2.2 4 (it has no syslog). Both fail RFC 1122, DHCP, TCP and HTTP, but v3.1 on 8 items and v2.2 on 25. Two of the shared failures are limits of the W5500 chip that no firmware can fix. The suite measures conformance, not the field failure: v3.1's main gain over v2.2 is recovery from (a) and (b), which the suite doesn't test.

2. Background

  • Product: Expromo EPS: six sequenced outputs (A0–A5, zero-cross SSRs) for LED display power, TCP control on port 5000, web page on port 80, inputs D5 (maintained), D6 (toggle), D9 (factory reset), RGB status LED on D2–D4.
  • Field firmware: v2.2 (Expromo_EPS_v2_2/), built on the Arduino Ethernet library 2.0.2. Older: v2.1.0 (6 ch) and v1.9.1 (6 ch, also a 10-ch variant in the field whose source isn't available).
  • Reported failure: a unit becomes unreachable at random: no web UI, no ping, no TCP commands, in static and DHCP mode. A reboot (power cycle) brings it back. Earlier theories (Cisco enterprise networks, EEE, the unit not announcing itself) had no supporting evidence.
  • MACs: Expromo owns the IEEE MA-S block 8C:1F:64:C3:9 (8C:1F:64:C3:90:00–9F:FF) and assigns one MAC per produced unit, never reused.
  • Controllers in use: Bitfocus Companion (module companion-eps), eXcontrol v0.3.1, Crestron, Q-SYS, the web page.

4. Methods

  • Pre-registration: for the A/B comparison and the W5500 hang tests, protocol and pass/fail criteria were committed to git before any data (docs/comparison-protocol.md 2026-10-08 17:59; docs/w5500-hang-tests.md 2026-10-09 00:15, amendments 08:04 and 08:22; docs/v3.1-standards.md test table 2026-10-09; docs/conformance-suite.md 2026-10-10, before either firmware was run).
  • Crossover: both firmwares run at the same time on two boards on the same switch, then swapped, so board differences and time effects cancel out.
  • Reporting: every failure is reported, including v3.0's. Rates come with exact 95 % intervals (Clopper–Pearson); with zero events, the one-sided bound 1 − 0.05^(1/n) ≈ 3/n.
  • Evidence grades: Measured (on the bench, repeated) · Preliminary (seen, too few tries) · Code-read (from source) · Unknown.
  • Fault injection reproduces a mechanism's effect (e.g. W5500 settings lost) with one register write in a test build. It does not reproduce its cause.
  • Read-only by default: the load and dose tests send only POWER_STATUS, PING, GET /, idle connections; the power test (outputs switched) ran only with nothing connected. No crafted or spoofed traffic was sent to the units.

5. Results

5.1 Code review of v2.2 (2026-10-08) — Code-read, later partly measured

  • The Arduino Ethernet library uses 4 of the W5500's 8 sockets on the ATmega328P. v2.2's UDP keepalive holds one permanently.
  • EthernetServer::available() hands over only connections that have sent data; silent connections are never closed. The W5500 keepalive is off, so half-open connections stay forever.
  • The stall watchdog needs 3 of 4 sockets busy; a state with one listener missing is invisible to it.
  • print(F()) sends every byte as its own TCP segment.
  • DHCP (library): a renew without a free socket freezes the lease state; a request blocks up to 60 s against an 8 s watchdog; after a boot without DHCP the unit stays on its fallback for good.
  • No W5500 health check; W5100Class::init() runs only once per boot, so the network can't be re-initialised without a CPU reset.
  • D4 (blue LED) is the KS0304's SD-card chip select.
  • v1.9.1: reboots after 60 s without a TCP exchange and always starts with the outputs off; its source already describes the stuck-socket symptom.
  • RAM/stack, watchdog/bootloader loop, EEPROM wear: ruled out (compiled: enough RAM; Optiboot; EEPROM.update).

5.25 Code analysis: v2.2 (with the Ethernet library), v3.1, v3.2 (2026-10-12) — Code-read, datasheet

All three firmwares and the Arduino Ethernet 2.0.2 source were read in full against the W5500 datasheet v1.1.0 (text extracted from WIZnet's PDF), the RFCs and AVR practice; stack frames were compiled with -fstack-usage. Full text with code references: docs/code-analysis.md.

  • No software-only cause for static-IP dropouts. After a successful start, neither v2.2 nor the library writes any register that decides whether the W5500 answers ARP or ping (SIPR, SHAR, SUBR, MR, PHYCFGR); only Ethernet.begin() in setup() does. A static unit can't silence itself by its own logic.
  • Three routes to "dead until power cycle" on v2.2, none of which it can leave: (D1) the chip loses its settings (§5.9; the library re-creates listeners on 0.0.0.0, the stall watchdog sees healthy sockets, the keepalive reads gateway 0 and skips); (D2) the PHY stops — v2.2's stall watchdog and keepalive return immediately whenever the link is down, so a PHY fault switches off v2.2's only recovery (the code-level reason for F7 in §5.24); (D3) the chip isn't detected when the library initialises it — begin() returns silently, every later linkStatus() retries the detection with a 560 ms delay, and if a retry succeeds the chip runs on IP 0.0.0.0 / MAC 0 with the LED blue. The only v2.2 recovery, a CPU watchdog reset, doesn't hardware-reset the W5500 (§5.17).
  • Leading trigger hypothesis: the supply. The Uno fuse sets the brown-out level to 2.7 V (confirmed on unit 3 by v3.3's fuse read, §5.26); the ATmega needs ≥ 3.78 V at 16 MHz and the W5500 ≥ 2.97 V on its 3.3 V rail. A 5 V-rail sag into ~2.9–4.0 V browns the W5500 out while the CPU runs on (D1/D2); a deeper one restarts the CPU, possibly before the chip is ready (D3). The 22 µF reset capacitor fixed the box's unreliable start from the 10 V PSU, which fits a slow supply ramp, but does nothing for sags in operation. Untested (needs USB unplugged).
  • Exposure. v2.2 sends every byte with its own SEND: ≈ 340 SPI writes and 82 TCP segments per POWER_STATUS vs ≈ 15 and 1–2 on v3.x. All bench polling of v2.2 (~10⁵ requests) only rules out per-request failure rates above ~3 × 10⁻⁵, while a unit polled once a second makes 2.6 × 10⁶ requests a month.
  • Other v2.2/library findings: the real TCP give-up is 18.4 s (library register bug), so a web client that stalls mid-page can make v2.2 hit its watchdog and drop the outputs; the library's chip detection probes W5200 framing first, which on a W5500 selects a reserved block the datasheet says "can cause the mal-function of the W5500".
  • v3.2 gaps: G1 the health check masks out the PHY reset bit (PHYCFGR bit 7; the datasheet says the PHY stays in reset while it is 0); G2 no recovery for a link that stays down; G3 the receiver check needs a gateway that answered since the last link-up, so it never fires on closed networks or for a receiver that goes deaf at link-up; G4 a W5500 that stops answering on SPI needs a hardware reset line the board doesn't have; G5 no supply visibility (Optiboot 4.4 clears the reset-cause flags before the sketch starts).

6. Discussion

What explains the field symptom. The total loss (no ping, no ARP) can only come from the W5500 not answering at all:

Mechanism Matches v2.2 recovers v3.0 / v3.1 recovers Trigger
DHCP strand: an unanswered renewal → v2.2 restart → no server within 60 s → static fallback for good exactly (DHCP mode only) no, until power cycle yes, by itself (6 s after the server returns) any DHCP outage or non-answer at renewal time
W5500 loses its settings exactly no yes, 3–6 s (v3.1: 2.1–6.9 s, 10/10, outputs kept) unknown; supply dip / ESD suspected; load switching untested

DHCP sites. The DHCP strand matches the field description exactly and needs no hardware fault: a router or DHCP server that is down, rebooting or slow when a v2.2 unit renews leaves that unit unreachable until someone power-cycles it. It does not apply to units set to static.

Static sites. Two candidates remain: the W5500 losing its settings (trigger untested: load switching), and deafness after a link negotiation (rare, persistence unknown). Withdrawn (2026-10-09): the earlier chain "v2.2's own CPU-only reboots come up deaf"; the deaf start-ups followed DTR resets, which also reset the W5500, and 19+ watchdog restarts never came up deaf.

Why v3.0 had 0/300 deaf start-ups is open: both firmwares got a W5500 hardware reset at each DTR reset; v3.0 additionally resets the PHY in software and negotiates a second time.

The Arduino Ethernet library is responsible for the starvation behaviour and the one-byte-per-packet output (§5.7). v2.2 made it worse (the permanent keepalive socket) and did not compensate.

v3.0 assessment. It fixes the reproduced defects and mechanism (a), and it matches or beats v2.2 everywhere it was measured. Five bugs were found and fixed during two days of testing (0x11 state, DHCP address per reboot, PHY reset on link bounce, PHY recovery assuming a gateway, identical temporary MACs). That is the expected cost of a rewrite; more may remain.

v3.1 assessment. It keeps v3.0's network layer and recovery, and adds standards conformance. On the final build every non-soak test passed, including settings loss with the outputs kept on, and v3.1 passed 46 of 56 conformance requirements against v2.2's 26. Its remaining failures are two chip limits, three small fixable items (ARP rate, Host, 414) and three deliberate trade-offs (DHCP from the fallback address, the 2-s send timeout, GET actions). Two bugs were found and fixed during the v3.1 work (a false conflict from the PC's own probe, and a timer in the split-command fix). It is not field-proven.

v3.2 assessment (recommended as the official firmware). It is v3.1 with the 5 s self-check widened to the mode (MR), retransmission (RTR/RCR) and PHY configuration (PHYCFGR) registers. In the pre-registered single-register fault matrix it recovered from all 14 faults with no "dead/needs-reset" outcome and the outputs never moving — including the four v3.1 died on (ping block, retry count 0, forced 10-half, and the PHY power-down that reproduces the field symptom, back in 11–12 s), and with no regression on the faults v3.1 already handled (§5.24). It scores the same 46 of 56 on the conformance suite (the change does not touch anything the suite measures). Cost: +118 B flash (31,238 of 32,256) and three extra SPI reads per 5 s cycle; the TCP protocol, stored settings and the v2.2 EEPROM downgrade path are unchanged. It is not field-proven; adoption should be followed by the hands-on and real-load checks and a pilot (§7).

v3.3 assessment (recommended as the official firmware). It is v3.2 with the gaps of §5.25 closed. In the overnight run it recovered from all 17 single-register faults (51 trials, 3–10 s, outputs never moved), including the PHY held in reset that leaves v3.2 dead; the link-down recovery alone brings a stuck PHY back in 40 s; the new receiver check sent one ARP request per check and made no false PHY reset when the gateway vanished; the whole regression suite passed. Twice in 40 settings-loss trials the chip came back deaf after the re-init's link renegotiation and cleared by itself (38 s, ~3.5 min; captured once, §5.26): mechanism (c), now seen on unit 3 too; faster detection after a re-init is the next step. Program memory is 99.5 % full (162 B free), so any later feature needs something taken out. It is not field-proven.

Is v2.2 as good as v3.1/v3.2 on standards? No. Several standards show FAIL for both, because one failed item fails a standard, but v2.2 fails 25 requirements against v3.1/v3.2's 8. Only v2.2 lacks conflict detection, gives up on TCP after 18.4 s, deviates from RFC 2131 in its DHCP client and mishandles HTTP methods.

7. Limits of the evidence

  • The field trigger is untested. Fault injection reproduces effects, not causes. There were no mains loads, no real power cuts (the USB reset keeps the W5500 powered) and no ESD, and only one enterprise switch so far (not yet exercised).
  • No field data. Site conditions and the failure rate are unknown. A reported customer failure turned out to be v1.9.1-10ch (source unavailable) and was not investigated.
  • Small numbers. Two boards; runs of minutes to 5 h; the deaf start-up rate rests on 4 events.
  • Confounding. The board difference is confounded with the switch port and cable until the port swap.
  • Author bias. The same person wrote v3.0 and the tests; mitigated by pre-registration, crossover, reporting v3.0's failures, and scripts anyone can rerun; not removed.
  • Unverified observation. The D6 press on a dead v2.2 unit (no reaction) needs a controlled retest.
  • Process issues during testing.
    • Claude Code stopped three background tasks under low PC memory: the DHCP scenario, a check-in timer, and the first H4 run.
    • Two packet captures didn't save (an argument-quoting issue, then fixed).
    • Another program intermittently held a USB port.
    • A planned test that emulated Cisco switch traffic was not run.
  • The 13:05 event had one observer (the PC) and no capture, serial or switch counters; it did not recur in 133 further flaps of that port.
  • DHCP results come from one server (the M4250's own); other servers may answer v2.2's renewals differently. The strand after an outage follows from v2.2's code for any server.
  • Conformance suite: one PC as the only peer, tools written by the same author; requirements that need forged traffic (defending an address, the 10th-conflict rate limit) are not verified.
  • v3.3 overnight run: one box on a direct cable and USB, unattended; the deaf receiver tested by emulation only; the link-down test reduced to 2 cycles to protect the PC adapter (amendment 1); two self-clearing deaf episodes after re-inits (§5.26). The supply-sag test, the decisive one for the static-mode hypothesis, was not run (needs hands-on time).
  • Not exercised in v3.0: real loads; recovery from a real deaf PHY; behaviour at 49+ days except the simulated rollover; DHCP NAK; two units on DHCP; multi-day operation.

9. Next steps

  1. Supply-sag test (hands-on, highest value): unit on a lab supply (or the 5 V rail sagged with a MOSFET), USB unplugged; sags to 2.8–4.5 V for 10–500 ms and slow power-ups (0.1–2 s), with and without the 22 µF; v2.2 vs v3.3, pre-registered. Decides the leading hypothesis (§5.25).
  2. Hardware for the next board revision: brown-out level 4.3 V (extended fuse 0xFC, ISP), a reset supervisor instead of the 22 µF capacitor, the W5500 reset pin on a free GPIO, the blue LED off D4.
  3. v3.3.1 candidates: fold the supply value into the re-init log record (log budget); stop alternating to a gateway that has stayed silent several times (faster deaf detection, §5.26); skip the receiver check while DHCP is renewing; faster deaf detection after a re-init (the two deaf episodes lasted 38 s and ~3.5 min; v3.3 acts after ~6 min where the configured gateway never answers).
  4. Field facts: for each failing site, DHCP or static; DHCP server/router type and whether it was down or rebooted around the failure.
  5. Field check before power-cycling a dead unit: on the site switch, is the unit's MAC still in the MAC table and is its port's receive counter rising? Yes → the unit still transmits (deaf receiver); no → it lost its settings or stopped.
  6. v3.1 by hand on unit 3, then on the showroom box with real loads: D5/D6/D9 and LEDs; real power cycles from the Netio with USB unplugged; flash with the box's own MAC (-DEPS_MAC_SUFFIX), capacitor removed for the upload; switch the loads with the poller and flight recorder running. Any REINIT/PHYRESET count or logged W5500 re-init is the finding.
  7. Persistence of the deaf state: catch a deaf start-up on unit 2 (DTR resets, register dump, switch counters) and leave it alone for ≥ 10 min.
  8. DHCP: a switch reload with the M4250 as DHCP server (the realistic outage); another DHCP server type.
  9. Pilot: v3.3 + flight recorder with per-unit MACs at sites that had failures. With no failure in N unit-days, the 95 % bound is ≈ 3/N.
